# /review — 독립 검수

목표: 만든 쪽이 아닌 눈으로 한 번 더 본다. 검수자는 고치지 않고 보고만 한다.

## 1. 범위 정하기

1. `project.yaml` 의 `modes.rigor` 와 `deploy.production_branch` 를 읽는다.
2. `git diff --stat <배포 브랜치>...HEAD` 와 `git status --short` 로 이번에 바뀐 파일을 확인한다.
   인자로 파일을 받았으면 그 파일만 본다.
3. 바뀐 내용으로 검수자를 고른다.

| 바뀐 것 | 부를 검수자 |
|---|---|
| HTML 본문, 섹션, CTA, 폼 | `conversion-reviewer`, `qa-tester` |
| title, meta, 헤딩, JSON-LD, sitemap, URL, 새 페이지 | `seo-reviewer` |
| 광고·랜딩·블로그 문구, 폼·푸터의 법적 요소 | `policy-reviewer` |
| JS, CSS, 빌드·배포 설정, 이미지 추가, Python·Actions·Workers | `tech-reviewer` |

4. 강도에 따라 조정한다.
   - `minimal`: 가장 관련 있는 1~2명만
   - `standard`: 위 표에 해당하는 검수자만
   - `full` 또는 인자 `all`: 5명 전원

## 2. 맡기기

- 서로의 결과가 필요 없으므로 **한 번에 동시에** 호출한다.
- 각 검수자에게 넘길 것: 볼 파일 목록, 비교 기준 브랜치, 이번 작업의 목적 한 줄, 기획서 경로(있으면).
- 넘기지 않을 것: 팀장의 의견, "문제없어 보인다"는 식의 선입견.

## 3. 종합하기

검수자의 보고를 그대로 옮기지 않는다.

1. `[차단]` 항목은 팀장이 해당 파일과 줄을 **직접 열어 사실인지 확인**한다. 틀린 지적은 버리고 이유를 적는다.
2. 여러 검수자가 같은 것을 지적했으면 하나로 합친다.
3. 서로 부딪치는 의견은 `.claude/docs/coordination-rules.md` 7번의 순서로 정한다.
   그래도 정해지지 않으면 선택지로 정리해 재욱님에게 올린다.

보고 형식

```
## 검수 종합 — [작업명]
검수자: (부른 사람) / 범위: 파일 N개

고칠 것 (차단): N건
1. 파일:줄 — 문제 — 조치
권장: N건
1. …
버린 지적: (틀렸거나 범위 밖인 것과 이유)
아무도 확인하지 못한 것: (실제 화면, 폼 전송, 실기기 등)
```

## 4. 고치기

- `[차단]` 은 고친다. 작은 수정은 팀장이 직접, 큰 수정은 `/delegate` 로 Codex 에 넘긴다.
- 고친 뒤 `/site-check` 를 다시 돌리고, 차단을 지적한 검수자에게만 재검수를 맡긴다.
- 분석 코드 변경, 삭제, 구조 변경이 필요한 조치는 고치기 전에 재욱님 확인을 받는다.
